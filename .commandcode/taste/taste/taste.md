# Taste
- Wants technical analysis explained in plain, simple terms ("explain more like for a baby") — dense write-ups packed with tables, dot-point jargon and metrics get pushed back; prefers the core idea spelled out simply first, detail after. Asks explicitly for definitions of terms/phrases used earlier and will quote the exact sentence back to ask what it means (e.g. "what is LOCO and that fold1 and fold2?", "what it mean" on a quoted claim about uncertainty). Confidence: 0.8
- When consulting on design/architecture decisions (e.g. model architecture or hyperparameter choices), wants analysis and recommendations only — states it as a standing rule ("rule: suggestion only, dont change anything", re-appended as "do not change anything" on later checks) and keeps asking for suggestions rather than edits ("suggest the fix", "suggest me … which to surpass the persistence") — so read code/data and report findings without editing files; implementation starts only on an explicit "implement"/"proceed". Confidence: 0.8
- When a new model/algorithm is to be added, wants it slotted in the way the existing ones are — asked for the paper-derived models to go "inside the deep learning section like other DL method", i.e. same placement, config entry, section layout and input/output contract, rather than a parallel structure invented for the new item. Confidence: 0.5
- Wants file-level accounting, not summaries of intent: when told work is done, verifies against the actual files and challenges it ("huh, what the implementation change did not applied to the training.ipynb and evaluation.ipynb?"), and repeatedly asks which artifact owns a behavior ("is loco inside the training.ipynb or just at run_loco"). Also asks for concrete end-to-end verification before running anything — that every model actually trains and that evaluation works given its run id, and whether a notebook run would spawn unexpected run-id folders rather than assuming. State which file/cell implements what, and back completion claims with the real contents. Confidence: 0.65
- Prefers settings that derive automatically from one primary knob instead of requiring manual re-synchronization — asked for validation to follow the rollout length ("on rollout 15 it uses 15 rollout validation … make it so adaptable so i don't need to change when changing the rollout training") rather than a second hand-edited setting. When adding a knob, make dependent behaviour follow it automatically. Confidence: 0.6
- When a plan or suggestion list is revised, wants the existing items preserved and extended rather than replaced — says "keep the suggestion above the 4 suggestion A, B, C, D" / "lets kept the suggestion inline" and then asks to "update above plan based on agreed plan", so carry prior items forward (marking what changed) instead of restating from scratch. Confidence: 0.5
- Approves a fix conditioned on it keeping the property under test genuinely intact, not just passing the check — chose the seeded-randomness option "if its still valid for validation" and expects the underlying behaviour (e.g. MC dropout's stochastic spread) preserved rather than suppressed to silence a failing guard. Confidence: 0.5
- Rather than dropping a feature because a dependency isn't installed, wants the dependency installed into the existing system Python — explicitly authorized `pip install --break-system-packages` ("implement the lightbgm, use the break system packages") when told the environment was externally managed and no venv existed; don't gate work on setting up a venv or on PEP 668, just install it (and note where it landed). Confidence: 0.6
- Wants the underlying misconception corrected before moving on to optimization suggestions — explicitly keeps a suggestion in reserve and asks to "fix the architectural misunderstanding first," then to elaborate on the suggestion; repeats this even after a full suggestion list has been given ("keep the suggestions … I'd like to fix the architecture before continuing implementation"). Confidence: 0.7
